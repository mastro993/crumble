# Recording with a process tap

A Note's Recording holds what was said in a meeting: the user's microphone and the call coming out of the Mac. Crumble records it as two tracks: the default input device, and a Core Audio process tap of every process's output except Crumble's own (`CATapDescription` initialised with `initMonoGlobalTapButExcludeProcesses:`, Crumble excluded by its bundle ID, made private, wrapped in a private aggregate device). Each track gets an IO proc registered with `AudioDeviceCreateIOProcID`. The bindings are `objc2-core-audio`, `objc2-audio-toolbox` and `objc2-avf-audio`, the family `crumble-eventkit` already uses; they cover taps, aggregate devices, ExtAudioFile and AVAudioEngine, so no other binding crate is needed. anarlog, an open-source meeting-notes app for macOS, builds its tap the same way through `cidre`.

## Rules

- **Two tracks, kept apart**: `mic.aac` and `system.aac` in `recordings/<note id>/` beside `crumble.sqlite3`. Transcription can then tell the user from the other side, and a silent track points at the permission that is missing. The tracks start back to back and may begin a few milliseconds apart; nothing aligns the files more finely. Only the echo canceller below lines them up, for its own use.
- **Mono AAC-LC in ADTS, at the device's sample rate** (usually 48 kHz, never resampled). ADTS frames each carry their own header, so a file cut off by a crash or force-quit plays up to its last packet. AAC in CAF was the first choice, but a CAF file killed mid-write read back as 0 packets, as its packet table is written at close; an `.m4a` needs its trailing `moov` atom. A test writes a file, never closes it, and reads it back. ExtAudioFile counts ADTS frames exactly; ADTS keeps no priming count, so a length read from a file runs up to ~70 ms long.
- **Callbacks never block.** An IO proc averages the first input buffer's channels to mono, cuts it into 1024-frame blocks stamped with the cycle's host time, and `try_send`s each by value over a bounded `std::sync::mpsc::sync_channel` of 512 blocks (about 10 s at 48 kHz), allocated once at start. A full channel drops the block and counts its frames; the count is logged at stop. The writer thread drains the system channel in full first, as it holds the microphone's reference, then takes up to 16 microphone blocks, so neither track starves the other, and sleeps 20 ms once both are empty instead of blocking on them, so an IO proc never has to wake it, which could take a lock. It encodes with `ExtAudioFileWrite`, marks a track heard once it gets anything but digital silence, and finalizes each file when its channel closes. A failed write ends that track's file there, rather than leaving a gap; it, a failed close, or no audio at all makes `Recorder::stop` return an error. An IO proc that cannot be unregistered keeps its queue alive, leaked rather than freed while Core Audio may still call it; the writer closes each file once stop is signalled and its queue is empty, so it never waits on that queue closing.
- **The Mac's sound is removed from the microphone.** On speakers the microphone hears the call too, so the mic track would hold the other side a second time, a little later, and transcription would credit the user with it. With both tracks, the writer thread runs WebRTC's echo canceller (AEC3, from the pure-Rust `sonora`) on the microphone before encoding it, with the system track as the reference, 10 ms at a time. AEC3 works at 48 kHz in three 16 kHz bands; a track at another rate is resampled to 48 kHz and, for the microphone, back.
  - **Below 8 kHz only AEC3's linear filter runs**, where speech and its echo are: it subtracts the echo it predicts from the reference, so a voice passes as recorded even while the call talks over it. AEC3's suppressor, which `sonora`'s `AudioProcessing` always runs after the filter, mutes whatever it cannot tell from echo; in the first version it muted a voice speaking over a video on loud speakers. In a simulation with recorded speech, the filter took 13 to 21 dB off the echo, least with speakers that distort, and kept the voice within 0.5 dB; AEC3 whole took 36 to 52 dB but cut the voice by 6 to 13 dB, and 32 dB in a test with the echo twice the voice. `sonora` exposes neither the filter's output nor the suppressor's tuning, so Crumble drives `sonora-aec3`'s block processor itself, with `sonora`'s band split, high-pass filter and resampler. Above 8 kHz, which the filter does not cover, the suppressor's output is kept: it removes the call's highs, and only a voice's highs are muted while the call talks over it.
  - **Each block's host time lines the pair up**, whichever device started first, across a gap, and as two devices' clocks drift apart. A microphone frame gets the reference from 50 ms after it, as the filter only finds echo that comes after its reference, even if a tap stamps its blocks a little after the Mac plays them; the reference is trimmed, or padded with silence, once it drifts more than 10 ms from there, and AEC3's own delay estimate covers the rest, the trip from speakers to microphone. The first version's 2 ms window lost most of the cancellation to 3 ms of jitter in the simulation. Paired by count instead, a tap that started 300 ms first lost all of it in a test. Core Audio stamps real devices' cycles with a host time; blocks without one fall back to that count pairing, logged once, and there a dropped block shifts the pairing for the rest of the Recording.
  - Every microphone sample comes out, cleaned, one for one; the microphone waits at most 500 ms for its reference, then is cleaned against silence. AEC3 gets the high-pass filter it needs on the microphone; there is no noise suppression and no gain control. It is always on: with no echo, the filter leaves the voice as it was, and headphones cannot be told apart reliably. Only the cleaned microphone is kept. A Recording with only one track, or a rate whose 10 ms is not a whole number of samples (such as 22 050 Hz), keeps the microphone as recorded. At most a full system channel's worth of reference, plus 500 ms, is held, so none the microphone still needs is lost after a stall, and a microphone that stops delivering cannot make it grow.
- **Permissions.** `Info.plist` carries `NSMicrophoneUsageDescription` and `NSAudioCaptureUsageDescription`. Record asks for the microphone through `AVAudioApplication` first, because registering an IO proc on the input device blocks while macOS's prompt is open. There is no public way to ask for, or read, system audio access: macOS prompts on the first tap and, until it is granted, the tap delivers silence. So silence is the signal: a track whose every sample stays under 1e-6 for the first 10 s brings up a line pointing to the System Settings pane that allows it. No private TCC API is used.
- **Playback**: one `AVAudioEngine`, a player node per track, both scheduled from the same position and started at the same host time; a seek stops and reschedules both. `AVAudioPlayer` was simpler, but it estimates an ADTS file's length from its bit rate: a 600 s file came back as 793 s.
- **Storage**: the database keeps `recording_started_at` and `recording_duration_ms`; a start without a length is a Recording still running or cut short by a crash. Stopping and launch recovery both go through `Notes::finish_recording`, which stores the length, or deletes a Recording with no audio. At launch, `Notes::recover_recordings` stores what each such Recording's files hold, and deletes one with no audio, as when it stopped before the first packet; one whose files cannot be read stays unfinished for the next launch, as they may still hold audio. `crumble-notes` owns the folder and its deletion; `crumble-audio` takes a folder and owns the file names in it.

## Considered Options

- **ScreenCaptureKit**: captures system audio too, but asks for Screen Recording, a broader permission than audio alone, and is built around display capture.
- **A virtual device such as BlackHole**: an install and a change to the user's output device, which is too much to ask for a calendar app.
- **One mixed track**: smaller, but transcription could not tell the speakers apart, and silence could not be traced to one permission.
- **WAV, as anarlog writes and later encodes**: crash-tolerant once its header is patched, but about 690 MB per track per hour of 32-bit float at 48 kHz.
- **A lock-free ring buffer crate** (`ringbuf`, `rtrb`): what anarlog uses. A bounded std channel of fixed-size blocks, polled by the writer, keeps the IO proc lock- and allocation-free without a dependency.
- **AVAudioEngine's input node for the microphone**: one more object graph, while the IO proc already written for the tap serves the input device unchanged.
- **Apple's voice processing (VPIO) for the echo**: no dependency, but it ducks every other app's audio, the call included, by about 8 dB even at its lowest setting; forces noise suppression on the voice; takes no reference of our choosing; runs only live; and whether it cancels other apps' audio on real speakers is disputed.
- **DTLN-aec through ONNX Runtime**, as anarlog does: a neural canceller, but at 16 kHz only, so the microphone would lose everything above 8 kHz; it adds a pre-release `ort`, a 7 MB model, and alignment code of its own, as it has no delay search.
- **tonarino's `webrtc-audio-processing`**: the same AEC3 in its original C++, but building it needs meson, ninja and abseil. `sonora` passes the upstream C++ test suite; if it falls short, the swap stays inside one module.
- **AEC3 whole, suppressor included**, as `sonora`'s `AudioProcessing` runs it: the first version. It took far more off the echo, but muted the voice wherever the call talked over it.
- **A milder suppressor**, AEC3's masking thresholds raised: in the simulation it kept the voice within 1.5 dB for 5 dB more off the echo, but lost 4 dB of it with louder echo. Any suppressor mutes the voice where the filter falls short.
- **Cancelling after Stop, from the two files**: Stop would take seconds per hour of Recording, crash recovery would need the same pass, and an AAC-coded reference cancels less well.
- **Cancelling only on speakers**, as anarlog does: it needs headphone detection, which AirPods, external DACs and docks defeat.

## Consequences

- About 65 kbps per speech track at the encoder's default bit rate, so about 30 MB per track and 60 MB per hour of Recording; silence costs far less.
- On speakers most of the call is removed from the microphone track, and the voice is never muted for it. A faint copy stays: what the filter cannot model, such as speakers that distort or a long room echo; tonal sound, such as a held chord, on which AEC3 adapts slowly; the call's first seconds, while the filter learns; and Crumble's own playback during a Recording, which the tap leaves out of the reference.
- `sonora` is a young, AI-assisted port (BSD-3), and Crumble uses its building blocks below `AudioProcessing`, which a new version may change; versions are pinned in `Cargo.lock`. The writer thread spends about 40 µs on each 10 ms of microphone in a release build.
- macOS 14.2 or later for process taps, and macOS 26 for excluding Crumble by bundle ID; the app already requires macOS 26.
- The input device is the default one when Record is pressed. Switching devices mid-Recording, as by connecting headphones, leaves that track silent or short; following the default device is a follow-up.
- Starting and stopping the devices runs on the main thread and can take a moment.
- `crumble-audio` uses `unsafe` for every Core Audio, AudioToolbox and AVFAudio call, so like `crumble-eventkit` (ADR 0001) it sets `unsafe_code = "deny"` with a `SAFETY` comment on each block, instead of the workspace's `forbid`.
- The Recording stays on the Mac until the user deletes it, or deletes its Note.
