# Native architecture

Crumble is a GPUI desktop application built with GPUI Kit components. The app shell layout is copied from [SkillBinder](https://github.com/mastro993/SkillBinder).

## Ownership

| Package | Responsibility |
| --- | --- |
| `apps/desktop` | Native lifecycle: window options, menus, key bindings, and quitting after the last window closes |
| `crates/ui` | GPUI root view: shell, sidebar, header, navigation history, pages, the Note detail view with its Recording controls, player and Transcript tab, the queue of Transcripts being made, and embedded icon assets. Changes stored state only through `Store` and `Notes` methods and never persists itself. Draws the Events `crates/sync` reads where `crates/calendar` places them, and holds only presentation state: focus, scroll, hover, motion, the minute redraws, the running `Recorder` and open `Player`, and the running transcription job |
| `crates/calendar` | Calendar logic without GPUI or IO: Calendar views, Periods and today; where Events fall on each day and how overlapping ones share columns; the Agenda list's rows with Quick notes among the Events, which days it reads next, how a read is split and filtered; links in Event descriptions |
| `crates/sync` | GPUI entities that read EventKit off the main thread and keep the result current: `CalendarSync` (access, Accounts, Calendars), `CalendarEvents` (the Calendar page's Events), and `AgendaEvents` (the Agenda's Events and the days they cover). Depends on GPUI core only, not on GPUI Kit |
| `crates/db` | The SQLite file `crumble.sqlite3`, the data folder it sits in, every migration, and the Diesel schema. Opens connections and runs pending migrations; holds no queries |
| `crates/store` | State kept across restarts, in the `crates/db` file with each change written as it happens, and Account rules without GPUI: Account order, colors and their tones, Aliases and labels, which Calendars show given Disabled and Hidden Accounts, and which state the Calendars section shows for the calendar access status |
| `crates/notes` | Notes and Quick notes in the `crates/db` file: creating, editing and soft-deleting them, and finding a Note's Event occurrence again; each Recording's start, length and folder, deleting that folder, and finishing Recordings a crash left running; each Note's Transcript, replaced whole, and which finished Recordings have none |
| `crates/audio` | Recordings without GPUI: `Recorder` captures the microphone and a process tap of the Mac's sound into two AAC files, removing the Mac's sound from the microphone, `Player` plays them together, `recorded_length` reads what the files hold, and `mic_access` asks for the microphone ([ADR 0005](../adr/0005-recording-with-a-process-tap.md)) |
| `crates/transcribe` | Transcripts without GPUI: `transcribe` reads a Recording's tracks with Apple's SpeechAnalyzer on the Mac and returns segments in time order, labelled by track; `model_status` and `install_model` manage the locale's speech model. The only Swift, behind a C ABI ([ADR 0006](../adr/0006-on-device-transcription-via-swift-bridge.md)) |
| `crates/theme` | Colors, typography, and dimensions |
| `crates/eventkit` | Read-only bridge to macOS EventKit: calendar access, Accounts, Calendars, Events, and change notifications as plain Rust data |

Code that does not need GPUI lives in domain crates rather than in `crates/ui`, as decided in [ADR 0002](../adr/0002-crates-split-on-gpui-boundary.md).

## Shell

- The macOS window uses a transparent titlebar. The traffic lights sit centred in the 50 pt header row. Other platforms keep native decorations.
- The sidebar toggle stays pinned beside the traffic lights whether the sidebar is open or closed. `Cmd-B` (`Ctrl-B` elsewhere) also toggles it. Opening and closing slide over 220 ms, and the slide is skipped when the system asks for reduced motion.
- You can resize the sidebar between 192 and 400 pt by dragging its trailing edge, or with the arrow, Home, and End keys on the focused handle. It starts at 232 pt. Width and collapsed state are not persisted.
- The back and forward arrows sit in the sidebar's header row. `Cmd-[` and `Cmd-]` (`Ctrl-[` and `Ctrl-]` elsewhere) do the same. They move through an in-memory route history, and each arrow is disabled when there is nothing to go back or forward to.
- The sidebar lists Home, Agenda, Calendar, and Chat at the top, the Calendars section below them (see Events), and Settings pinned to the bottom. The sections scroll between the top rows and Settings; a hairline divider shows on either side while rows are scrolled out of view behind it, and the scrollbar fades in only while the pointer is over the sidebar. Clicking a section's title, or pressing Enter or Space on it, folds its rows away with a short slide and a turning chevron, and the folded sections are saved as rows of the `folded_sections` table. The section layout is copied from SkillBinder. Clicking a row, or pressing Enter or Space while it has focus, opens its route and records the previous one for Back. The app starts on Home. Home and Chat show only their title for now.
- The theme follows the window's light or dark appearance.
- The header and the page share 24 pt horizontal padding (`CONTENT_PADDING`), so header controls line up with page content. With the sidebar collapsed, the header's leading edge moves right to clear the sidebar toggle.
- While a Recording runs, the header's trailing end shows a pill, a red dot and "Recording · 12:03", on every page; clicking it opens the Note being recorded (see Recording).
- Double-clicking empty header space zooms the window, and dragging it moves the window. Presses on header buttons and tabs stay with the control, so they never zoom or drag the window.

## Calendar

Terms such as Calendar view, Period, and Focused date are defined in [CONTEXT.md](../../CONTEXT.md).

- The Calendar page shows one Period in a Week, Month, or Year Calendar view. It opens on today in the Calendar view last picked, with the switcher or by clicking a Month day or a Year month, which is saved in `app_state.calendar_view` and starts as Month view. The Focused date stays in memory while the app runs and is not persisted.
- On the Calendar route the header holds Today, Previous, and Next buttons, the Period title, and a segmented Week | Month | Year switcher. The title truncates when the header is too narrow.
- `Cmd-T` jumps to today and `Cmd-←` / `Cmd-→` step one Period (`Ctrl` elsewhere). These shortcuts are handled only while the Calendar page is open.
- Week view is an hourly grid from 00:00 to 24:00 that scrolls on its own. It opens scrolled to 08:00 and keeps its scroll position while the app runs. In the week that holds today, a red line marks the current time across every day, thicker on today and starting there from a dot, with the time in red in the hour column in place of an hour label it would overlap. It is drawn over the Events and moves at the start of each minute. Month view stretches 4–6 week rows to fill the page and mutes days from neighbouring months. Clicking a day opens its week in Week view; clicking an Event opens its page instead. Year view shows twelve months as rounded cards in a 4×3 grid. Each card always has six week rows, so the cards in a grid row end level, and the grid stays at most 1200 pt wide. The current month's name is bold. Clicking anywhere on a month card opens that month in Month view. Clickable days and month cards show a pointer cursor.
- Week and Month grids sit in a bordered frame with 12 pt rounded corners (`SURFACE_RADIUS`). Shaded cells in the corners follow the curve, including while the Week hours scroll.
- Today is circled in the accent color. Weekends (Saturday and Sunday) are shaded in every Calendar view. In Year view, adjacent weekend columns share one rounded strip.
- Today is read from the local clock on every render, so a window left open past midnight updates on its next redraw.
- Week and Month views draw the Events of the dates on screen, from every Calendar that is not Disabled and whose Account is neither Disabled nor Hidden; Year view draws none. Each Event takes its Account's color (see Events), so every Calendar of an Account shares it. The Events are read off the main thread again when the Period, the Calendar view, the First day of week, a Disabled or Hidden choice, or EventKit changes. A failed read is logged and the last Events stay.
- In Week view, timed Events are blocks placed by time over their day's column, at least 22 minutes tall so short ones stay clickable, with 6 pt after each block and 4 pt between one block and the next below it. Overlapping Events share the column side by side. Blocks under 45 minutes show only their title. An Event crossing midnight is drawn on each day it touches, and one that ends at midnight stays on the day before. All-day Events sit in a strip between the day names and the hours, two per day before "+N more".
- In Month view, each day lists its all-day Events as tinted bars, then its timed Events by start as a colored dot, the start time, and the title. A day shows three before "+N more".
- Resting the pointer on an Event for 500 ms shows its details card beside it: the title in up to two lines, when it happens, the description flattened into up to three lines, each cut with an ellipsis, the first three participants before "+N more", and a full-width Join button named after the meeting service when it has a meeting link. The card opens to the right of the Event with their top edges level, flips to the left when the window has no room on the right, and stays at least 8 pt inside the window, so it never covers its Event. It closes 150 ms after the pointer leaves both the Event and the card, so the pointer can cross the gap to reach its Join button. Crumble draws the card itself instead of using GPUI Kit's `HoverCard` (see Cards).
- Clicking an Event, or pressing Enter or Space while it has focus, opens its page, and Back returns to the Calendar page. Tab reaches each Event. The Calendar row stays selected in the sidebar. The page shows the Event's Note in the Note detail view (see Notes). Its header holds a breadcrumb, "Calendar › title", whose Calendar opens the Calendar page and whose title truncates, then on the right a description button, a participants button showing how many were invited, and a Join button named after the meeting service, then the Note actions button once the Event has a Note. Each button shows only when the Event has what it opens. The description and participants buttons open a 360 pt wide card 16 pt below them, right-aligned with them, which scrolls past 420 pt and closes when clicked away from or with Escape (see Cards). The participants box lists everyone. In the description box, web links and linked text are underlined in the theme's link color and open in the browser when clicked; the hover card shows linked text without its address. The header shows the Event as it was when it was opened, or as last read while it is still in the Calendar page's dates, so an EventKit change shows up there. A moved Event is found again by its series UID and occurrence, unless more than one Event in those dates has them, as when one Event shows in two Calendars.
- Each participant shows an icon for their answer (accepted, maybe, declined, delegated, or awaiting), with the name struck through when they declined, and "Organizer" or "You" after the name. Hovering the row names the answer. Crumble never changes Events.

## Agenda

Agenda page, Agenda list, and In progress are defined in [CONTEXT.md](../../CONTEXT.md).

- The Agenda page lists every Event that has started: timed Events whose start has passed and all-day Events whose first day is today or earlier. It uses the same Calendars as the Calendar page: none that is Disabled or whose Account is Disabled or Hidden. It also lists every Quick note listed in the days it has read, whatever is Disabled or Hidden. The header shows no title; it holds a New note button on the left, left out without calendar access, and, while the selected row has a Note, the Note actions button on the right (see Notes). New note makes a Quick note now, selects its row, and focuses its Memo; if it cannot, the error is logged and a "Couldn't make a note" toast shows.
- The Agenda list is a 320 pt column running from the sidebar's edge to the window's bottom, with a hairline on its trailing edge. Its surface runs from the window's top, behind the header, in a shade between the sidebar's and the page's, so it reads as a second sidebar. Rows scrolled past the list's top fade out over its top 32 pt instead of being cut off; the fade grows in over the first 32 pt scrolled, so the list at rest is not dimmed. It is not resizable and stays when the sidebar collapses. The content area beside it shows the selected row's Note in the Note detail view, and is empty while no row is selected.
- Days run newest first under a header: "Today", "Yesterday", then the date, with the year only outside the current year. Each Event is listed once, under the day it started, except that In progress Events sit at the top of Today whatever day they started. Below them a red line with a dot marks now, as in Week view; then come Today's all-day Events and its ended Events, newest first. Other days list their all-day Events first, then the rest newest first. A Quick note sits under the day of its Recording's start, else the day it was made, at that time, among the timed Events; a day with only Quick notes still gets its header.
- An Event row shows a bar in its Account's color, the title on one line, and the time: "09:00 – 10:30", "All day", or both dates for an Event across days, as the details card writes it. A Quick note row shows a neutral bar, its title or "Quick note", and the time it is listed at.
- Clicking a row, or pressing Enter or Space while it has focus, selects it; Tab reaches each row. The selected row is filled as a selected sidebar row is, and the others fill on hover. The selection stays while the app runs and when the list is built again: an Event that moved is found again by its series UID and occurrence, and a row that is gone clears it, as losing calendar access does.
- The list reads the last 30 days first, then 30 more days back at a time while it holds fewer than 40 rows or is scrolled within 20 rows of its end, skipping empty stretches. It stops five years back with "End of Agenda", or "No past Events" when it found none. Each read runs off the main thread, in pieces of at most a year, since EventKit searches at most four years at once. The read that covers today also keeps timed Events that started before it and are still In progress. A failed read is logged and the last Events stay; it is not tried again until EventKit reports a change or a different read is wanted.
- The Agenda reads nothing until it is first opened. Its Events and scroll position stay in memory while the app runs. The days already read, never more than five years back, are read again when the day changes, when a Disabled or Hidden choice changes, or after EventKit reports a change. Quick notes are read from `crates/notes` each time the rows are built; a failed read is logged and the last Quick notes stay. While the Agenda is open, it updates on each minute, so an Event joins the list when it starts and leaves In progress when it ends.
- Once the list is scrolled away from its top, a round button with an up arrow floats centered near the column's top. Clicking it scrolls the list back to the top over 300 ms, or at once when macOS asks for reduced motion; scrolling by hand stops it. The button goes away once the list is at its top.
- Without calendar access the column says to connect calendars from the sidebar.

## Events

Crumble reads Events from macOS EventKit and never changes them; see [ADR 0001](../adr/0001-read-only-events-via-eventkit.md). Account, Calendar, and Event are defined in [CONTEXT.md](../../CONTEXT.md).

- `crates/eventkit` is the only crate that calls Objective-C. Every EventKit call is `unsafe`, so it sets its own lints with `unsafe_code = "deny"` and local allows, while the other crates keep the workspace's `forbid`. On other platforms it reports `Access::Unsupported` and returns nothing.
- Calls go through one shared event store. EventKit exceptions, raised when its connection to the calendar daemon drops, and nils from getters declared non-null become errors instead of crashing the app.
- Accounts are the macOS sources that hold at least one event Calendar, sorted by name. Their provider is guessed: Exchange is Outlook, a CalDAV source titled "iCloud" is Apple, and a CalDAV title containing "gmail" or "google" is Google. Any other CalDAV source is Google when one of its Events within 90 days of today has an external identifier ending in `@google.com`, which catches Google Workspace accounts on their own domain. Anything else is Other.
- EventKit has no email field either, so an Account's email is inferred: the user's own `mailto:` address as organizer or attendee of an Event within 90 days of today, read only for CalDAV and Exchange sources, else the one Calendar named after an address, as Google names an Account's main Calendar. Two Calendars named after addresses are ambiguous, because shared Calendars carry other people's addresses, so neither is used.
- Calendar colors are converted to sRGB. Events are returned one per occurrence, with declined and cancelled ones left out. All-day Events are whole dates; timed Events are in the system time zone. A join link is the first Google Meet, Microsoft Teams, Zoom, Webex, FaceTime, Whereby, Jitsi Meet, GoTo Meeting, or Amazon Chime link found in the Event's URL, then its location, then its notes, and it carries the service's name. The description is the notes as plain text: HTML, as Google sends a description edited on the web, becomes text, with a link whose text is not its address kept as `[text](address)`; the block of meeting details Google or Teams adds between marker lines goes when it holds a meeting link; and every meeting link left is removed, since the Join button stands for it. Participants are the Event's attendees with their names, else their addresses, and answers, the organizer first; EventKit often lists the organizer among the attendees too, so that entry moves first rather than repeating. An Event without attendees has no participants. Each Event's `id` is unique per occurrence within one run but changes when the Event moves. To find an Event again, it also carries `series_uid`, its iCalendar UID with any `/RID=<seconds>` suffix of a detached occurrence removed, `None` until the Event syncs to its server; and, for a repeating or detached occurrence, `occurrence`, its original start, which moving it does not change: a local date for an all-day one, the wall time read as UTC for a floating one with no time zone, else an instant. [ADR 0004](../adr/0004-event-identity-for-notes.md) has the rules.
- EventKit is read only in `crates/sync`. The root view asks its loaders for Events with the dates and the shown Calendar ids, and redraws when they finish reading. `CalendarSync`, owned by the root view, holds the access state, the Accounts, and the Calendars. At launch it reads them only if access is already granted, so Crumble never prompts on its own. It reads again whenever EventKit reports a change, off the main thread. A failed read is logged and the last data stays on screen.
- The sidebar's Calendars section sits below Chat. Its rows are the Accounts that are not Disabled, each after a checkbox in the Account's color and labelled with its Alias when it has one, else with its email when one is found, else with its System Settings name. The checkbox is filled with the color and holds a check while the Account is shown, and is only outlined in it while the Account is Hidden. The color starts as one from SkillBinder's folder palette picked from a hash of the Account's identifier, so it looks random but stays put without being saved. Clicking a row, or pressing Enter or Space while it has focus, Hides or Shows the Account; the row reads as a checkbox to assistive technology. Hidden Accounts are saved in `accounts.hidden`, and Disabling and Enabling a Hidden Account leaves it Hidden. Dragging a row reorders the Accounts without changing whether it is Hidden: the row floats under the pointer while the others slide aside, and the order is saved in `accounts.position` and also used by Settings. Disabled Accounts keep their place in that order while they are left out of the sidebar. Accounts not in the saved order follow, sorted by name. Right-clicking a row opens a context menu (see Context menus) that renames the Account, has a Color submenu with a dot per color and a check on the current one, and moves it up or down. Below the palette, the Custom row opens a third menu level beside the submenu (see Context menus) that holds GPUI Kit's headless color picker, laid out as GPUI Kit lays out its own palette: a row of shades from dark to light for each of nine hues, then a hex field beside the hovered or current color. Choosing a shade, or entering a hex value and pressing Enter, picks that color, saves it, and closes the menu. A custom color drops any transparency and looks the same in light and dark mode, while each palette color has a lighter tone for dark mode. Custom leads with an empty ring until a custom color is picked, then with its dot and a check. Move Up is disabled on the first row and Move Down on the last. The row keeps its hover fill while its menu is open. Rename turns the row into a field after its checkbox, holding its name, all selected: Enter or clicking away saves it, and Escape cancels. The drag and its slide are copied from SkillBinder. A picked color is saved in `accounts.color`, marks the Account in Settings, and colors its checkbox and its Events on the Calendar page. As in SkillBinder, no keyboard shortcut opens the menu. Before access is asked the section shows one "Connect calendars" row that opens the macOS prompt. After a refusal it shows "Allow calendar access", which opens Privacy & Security › Calendars. With access and no Accounts it shows a hint that opens Internet Accounts. When every Account is Disabled it shows a hint that opens Settings. Accounts are added and removed in System Settings, so the section has no add or delete action. On platforms without EventKit the section is hidden.
- macOS grants calendar access only to an app bundle whose `Info.plist` has `NSCalendarsFullAccessUsageDescription`. `apps/desktop/Info.plist` holds it, and the macOS Cargo runner (`scripts/macos-runner.sh`) wraps `crumble` in `Crumble.app`, signs it, and launches it with `open`. Ctrl-C quits the app too. Test binaries run directly.

## Context menus

- Crumble draws its own context menu (`native_view/menu`) instead of GPUI Kit's `PopupMenu`, which fixes its row height, separators, and corner radius, and has no opening animation.
- A menu opens with its top-left corner at the pointer, or 4 pt below the leading edge of the button that opens it, as the Note actions button does, and stays at least 8 pt inside the window. It has 12 pt rounded corners (`SURFACE_RADIUS`), 8 pt of padding, a hairline edge drawn as a ring so a submenu covers it, and a soft shadow. Its surface is the popover color in light mode and the muted color in dark mode, a step above the sidebar. The metrics are in `crumble_theme::menu`.
- Rows reuse the sidebar row height and icon metrics: 32 pt tall with a 16 pt icon in the muted color. Labels are 13 pt, the macOS menu size. A checked row shows a check at its trailing edge, and a row with a submenu shows a chevron. Enabled rows show the pointing-hand cursor; disabled rows are dimmed, keep the arrow, and cannot be highlighted. Separators are hairlines inset to the row width.
- The menu fades in while sliding 4 pt down onto its place, using the theme's fast duration and enter curve (120 ms). The motion is skipped when the system asks for reduced motion. Submenus and panels appear without motion, and a menu closes without motion.
- A submenu opens when the pointer moves onto its row, when its row is clicked, or with Right, Enter, or Space, which also highlight its first row. It overlaps the menu's edge by 4 pt with its first row level with the row it opened from, and it flips to the left when the window has no room on the right. When the pointer moves onto another row, including a disabled one, the submenu stays open for 150 ms, so a diagonal move toward one of its lower rows can cross the rows in between. Only one level of submenu is supported, but a submenu row can open a panel of any content beside it as a third level, such as the Custom color picker. A panel opens and closes as a submenu does, with the same 150 ms delay, and Right, Enter, or Space open it and move focus into it. Keys used in the panel, such as a hex field's, stay in it and never close the menu. Escape or Left closes the panel and gives focus back to the menu, which also takes focus back when the panel closes while holding it.
- The menu takes keyboard focus. Up and Down move the highlight, skipping separators and disabled rows and wrapping around. Left closes the submenu while the highlight is in it. Enter or Space chooses the highlighted row. Escape closes the submenu, or the menu when no submenu is open.
- Choosing a row closes the menu and then runs it, so an action that moves focus, such as Rename, keeps it. Otherwise focus returns to where it was before the menu opened, or to the root view when that element is gone, so the window's shortcuts keep working.
- While a menu is open, a backdrop covers the window: a press anywhere outside the menu closes it and does not reach what is underneath, and the content underneath does not scroll or show hover. The menu also closes when Tab moves focus away, when a shortcut such as `Cmd-B` runs while focus is not in a panel, or when the app goes to the background.

## Cards

- A card floats over the window with content such as an Event's details, opened by resting the pointer on an element or by clicking a button. Every card comes from `native_view/card`, so they share one look: the context menu's surface, corners, edge, shadow, and opening motion (see Context menus), with 16 pt of padding, twice a menu's, and the window's line height whatever the element it opens from uses.

## Settings

- `crates/store` keeps the choices made in Settings, with the rest of the state Crumble keeps across restarts, in the SQLite database `crumble.sqlite3` in the platform data directory (`~/Library/Application Support/Crumble` on macOS), creating the folder when missing. `crates/db` opens the file and runs pending migrations; `crates/store` then reads its tables into memory; views read from memory, and each change is written in its own transaction on the main thread. If the database cannot be opened, migrated, or read, the error is logged and the app runs on the defaults in an in-memory database for that run, leaving the file alone. A stored value that no longer decodes falls back to its default. If a write fails, the error is logged and the app keeps the new value in memory. `settings.json`, used before the database, is no longer read: preferences saved there reset once.
- The tables are `app_state` (one row: `first_day_of_week`, 0 for Monday, and `calendar_view`), `accounts` (by EventKit identifier: `position` in the user's order, `color` as a palette name or `#rrggbb`, `alias`, `disabled`, `hidden`), `calendars` (by EventKit identifier: `disabled`) and `folded_sections`. An Account or Calendar row is written the first time the user changes it and kept after its values return to the defaults.
- **First day of week** can be any weekday and defaults to Monday. It sets the column order of every Calendar view and where each week Period begins.
- **Calendars** lists every Account with an Alias field and a switch, and under it its Calendars, each with a checkbox, its macOS color, and its name. Settings is the only place to Disable or Enable an Account or a Calendar. An Account with an Alias is titled with it, followed by its own name in brackets. Each keystroke in the field saves the Alias. A blank Alias, or one equal to the Account's own name, is removed, so the sidebar's Rename and the field agree. Aliases are saved in `accounts.alias`. Every Account and Calendar starts enabled; turning an Account's switch off or unchecking a Calendar Disables it. A Disabled Account greys its Calendars out and keeps their checkboxes as they were. The group is hidden while access is not granted. Disabled Accounts and Calendars are saved by EventKit identifier in `accounts.disabled` and `calendars.disabled`, and change nothing in macOS.

## Notes

Note, Quick note and Memo are defined in [CONTEXT.md](../../CONTEXT.md).

- One Note detail view shows the Note of the selected Agenda row and of the opened Event page: a Quick note itself, or the Event occurrence's one Note, if it has one. It reads it again whenever what it shows changes, synchronously on the main thread; a failed read is logged, shows nothing, and is tried again on a later redraw; an Event that moves is still the same occurrence, found by its series UID and occurrence, so its Note stays as it is. `Notes` is owned by the root view beside `Store`.
- At the top is the Note's title, large and editable in place. While it is empty its placeholder is the Event's title, kept current as the Event changes, or "Quick note". Enter or leaving the field saves it, and an empty title is saved as none; a failed save is handled as the Memo's is below. Below it, in muted text, is when the Event happens, as the details card writes it, or when the Quick note is listed: its Recording's start, else when it was made. An Event with no Note shows its title as plain text.
- Below the title is a card with a tab bar, then the tab. The tabs are Memo, then Transcript once the Note has a Transcript or one is being made (see Transcript); a Summary tab will come first. The bar's trailing side holds the Recording controls (see Recording). The tab the user picks stays picked across Notes while the shown Note has it; otherwise the first tab shows. The Memo is a field that grows with its text. It is saved 500 ms after typing pauses, at once when it loses focus, before another row shows, and when the window closes or the app quits. A failed save is logged, says "Couldn't save" under the card, and keeps the text in memory, which is shown again in place of the stored Memo and tried again on every later save of any Note, until it is written. While any still fails, closing the window asks first in an alert, as closing loses it; quitting does not ask. An Event with no Note shows "No note yet" in the card with a New note button, which makes the occurrence's Note, shows it, and focuses its Memo, and a Record button, which does the same and starts recording it. If the occurrence has a Note by then, as when another Calendar's copy of the Event made one, that Note shows instead of a second.
- The Note actions button, a "…" icon, sits on the right of the page header while there is a Note. Clicking it opens a menu below it (see Context menus) with Transcribe again and Delete recording when the Note has a Recording that is not running (Transcribe again only while no Transcript of it is waiting or being made), and Delete note. Transcribe again asks first when there is a Transcript, as the new one replaces it. Delete recording asks first in an alert, then deletes the audio, clears the Recording, and deletes its Transcript. Delete note asks first in an alert, since nothing brings a Note back, and deletes its Recording's audio too, stopping it if it is running. A deleted Event's Note leaves the card empty again; a deleted Quick note's row leaves the Agenda and the selection clears.

- `crates/notes` keeps Notes in the `notes` table of `crumble.sqlite3`, through its own connection beside the one `crates/store` keeps. The file runs in WAL mode with a 5 s busy timeout, so one connection reads while the other writes. If the file cannot be opened, Notes use an in-memory database for that run and are not kept; their Recordings go to a temporary folder, deleted when `Notes` is dropped as the app quits.
- Each row has a UUID v7 `id`, an optional `title`, the `memo`, and `created_at`, `updated_at` and `deleted_at` as RFC 3339 UTC text to the millisecond. Every change sets `updated_at`. Deleting a Note first deletes its Recording's folder, then sets `deleted_at`, and every read skips it; a deleted Note cannot be edited or brought back. Its row stays only as a tombstone for sync, keeping its id and timestamps: the transaction that sets `deleted_at` also clears its title, Memo, Event key and snapshot, Recording and Transcript columns, and deletes its Transcript segments. A folder that cannot be deleted leaves the Note, or its Recording, in place to try again, so no audio is left behind unreachable.
- A Note attached to an Event keeps the Event's key, `event_series_uid` and `event_occurrence`, and a snapshot of its `event_title` and `event_start` ([ADR 0004](../adr/0004-event-identity-for-notes.md)). An occurrence and a start are stored as `2026-10-13` for an all-day one or `2026-10-13T07:00:00Z` for a timed one. A Quick note has all four `NULL`.
- An Event occurrence has at most one Note, shared by every Calendar that shows it: the Note whose key matches it (the same UID, and the same occurrence or none for both), else the oldest whose snapshot matches its title and start and that has no UID or the Event's own. The snapshot finds a Note made before the Event synced, or one whose occurrence key changed; it never matches a Note keyed to another UID, so two Events with the same title and start keep their own Notes. Making a Note for an Event that has one returns that Note. A unique index on `(event_series_uid, IFNULL(event_occurrence, ''))` over live keyed Notes refuses a second one; the `IFNULL` is there because a UNIQUE index tells NULLs apart. Reading never rewrites a stored key, and a Note whose Event is gone is kept.
- Quick notes are listed newest first by `COALESCE(recording_started_at, created_at)`, the expression the `notes_quick` index is on.
- A Recording is `recording_started_at` (RFC 3339 UTC, to the millisecond) and `recording_duration_ms`, both `NULL` without one. A start with no length is a Recording still running, or one a crash cut short.
- A Transcript is `transcript_model`, `transcript_locale` and `transcribed_at` on the Note, all `NULL` without one, and its rows in `transcript_segments`: `note_id`, `track` (`mic` or `system`), `start_ms`, `end_ms` and `text`, read in `start_ms` order. `Notes::set_transcript` replaces a Transcript in one transaction, hard-deleting the old segments, and needs a finished Recording. Deleting the Recording or the Note deletes its Transcript.

## Recording

Recording is defined in [CONTEXT.md](../../CONTEXT.md); the design is [ADR 0005](../adr/0005-recording-with-a-process-tap.md).

- A Recording is two files in `~/Library/Application Support/Crumble/recordings/<note id>/`: `mic.aac`, the default input device, and `system.aac`, a process tap of every process's output except Crumble's. Each is mono AAC-LC in ADTS at the device's own sample rate, usually 48 kHz, at the encoder's default bit rate: about 65 kbps for speech, so about 30 MB per track and 60 MB per hour of Recording, and far less for silence. ADTS stays playable up to the last packet written when the app dies. `crates/notes` names the folder from the Note id and deletes it; `crates/audio` names and writes the files in it.
- The card header's trailing side shows, by state:
  - No Recording: Record, with a microphone icon. The first time, it asks macOS for the microphone, then starts whatever the answer: a denied microphone still records the Mac's sound. While another Note records, Record is disabled and its tooltip names that Note.
  - Recording: a red dot, the elapsed time, redrawn each second, and Stop.
  - Recorded: play or pause, a scrubber, and `position / length`. Playing past the end starts again from the beginning.
- Starting stores `recording_started_at` and stopping stores the length, the longest track's frame count. A length that fails to save is handled as a failed Memo save: the Recording shows as finished, "Couldn't save" shows, and the length is written again with every later save; a restart reads it from the files instead. A Quick note's row moves to the Recording's start. A track that cannot open or start is left out, and the Recording fails only when neither starts. A Recording that cannot start is forgotten and the card says "Couldn't record". A track whose encoder fails stops taking audio, so its file holds what came before the failure; stopping then keeps what the files hold and says "Couldn't record" too. The line shows only under the Note it is about, and goes once that Note's next start, stop or delete succeeds.
- One Recording runs at a time in the app, and it keeps running while other pages show. Quitting or closing the window stops it like Stop does; when closing asks first, only once the window closes. Stop and launch recovery keep a Recording through `Notes::finish_recording`, which stores its length, or deletes it when it holds no audio. At launch, `Notes::recover_recordings` does so for each Recording a crash left running, with the length its files hold; one that fails does not stop the others. Stopping before any audio arrived deletes the Recording the same way, with no error shown. A Recording whose files exist but cannot be read is never deleted for it: it stays unfinished, and the next launch reads it again.
- A recorded track that has heard only digital silence (every sample under 1e-6) for the first 10 s shows a line under the card with an Open System Settings button: for the Mac's sound, the Screen & System Audio Recording pane (`Privacy_ScreenCapture`), since a tap without permission hears silence; for the microphone, the Microphone pane. Once a track hears sound, its line goes.
- The IO procs copy each Core Audio cycle into 1024-frame blocks, stamped with the cycle's host time, and send them over a bounded channel to a writer thread, which encodes up to 16 microphone blocks before turning to the other track, and with both tracks drains the system track first, as it is the microphone's reference; a full channel drops the block and the drop count is logged at stop.
- With both tracks, `mic.aac` has the Mac's sound removed, as on speakers the microphone hears the call too. Before encoding, the writer runs WebRTC's echo canceller (AEC3, through `sonora`) on the microphone, with the system track as the reference, paired 10 ms at a time by host time. Only echo cancellation runs: no noise suppression and no gain control. The microphone waits at most 500 ms for its reference, then is cleaned against silence. It is always on, headphones or not. Crumble's own playback is not in the reference, so playing a Recording on speakers while another records stays in the mic track. Starting the devices happens on the main thread.
- Playback runs both files through one `AVAudioEngine`, a player node each, scheduled from the same position and started at the same host time. The player is opened when a Note with a finished Recording shows, and dropped when another row or page shows.

## Transcript

Transcript and Model are defined in [CONTEXT.md](../../CONTEXT.md); the design is [ADR 0006](../adr/0006-on-device-transcription-via-swift-bridge.md).

- When Stop ends a Recording and its length is stored, its Note is queued to be transcribed; a length kept in memory after a failed save is queued once it saves. A Recording stopped by quitting, closing the window or deleting its Note is not queued. At launch, after recovering Recordings, every Note whose finished Recording has no Transcript is queued, as when the app quit mid-transcription; nothing partial is kept. Transcribe again and Try again queue it too. One job runs at a time, first come first, on GPUI's background executor; it sends its progress and result over a channel, and the result is stored through `Notes` on the main thread. Deleting the Recording or the Note drops its job's result. A call into Swift cannot be stopped, so a job already running finishes unseen, and the next one waits for it.
- A job transcribes in the Mac's current locale (`Locale.current`). If that locale's speech model is not installed it downloads it first, Apple's shared on-device asset of a few hundred MB per language. Then it transcribes `mic.aac` and `system.aac`, whichever exist, each on its own, and merges their segments in time order. The Model is stored as "Apple SpeechAnalyzer".
- The Transcript tab shows, by state:
  - Waiting behind another job: "Waiting to transcribe…".
  - Downloading the model: "Downloading the speech model for English (United States)… 42%" with a progress bar.
  - Transcribing: "Transcribing… 42%" with a progress bar.
  - Failed: "Couldn't download the speech model.", "Couldn't transcribe this recording." or "Couldn't save the Transcript.", with Try again; the error is logged.
  - The locale cannot be transcribed: "Transcription isn't available for <language> on this Mac.", with no other language tried.
  - Done: "Transcribed by Apple, on this Mac" in small muted text, then one line per segment: its start as `m:ss`, a link that seeks the player there; "You" for the microphone or "Others" for the Mac's sound; and the text. A Transcript with no segments says "No speech was heard."

## Agent automation

- `cargo run -p crumble --features mcp` installs a [gpui-mcp](https://github.com/themixednuts/gpui-mcp) bridge on the main window under the app ID `crumble`. The `gpui-mcp` server in `.mcp.json` finds it, and agents can then read the semantic tree, click, type, and take window screenshots through GPUI's own event pipeline instead of the system mouse. Builds without the feature carry no bridge.
- The bridge needs GPUI automation hooks, so the workspace patches `gpui-pre` with gpui-mcp's copy for every build. The bridge and the patch are pinned to the same gpui-mcp revision as the installed server; update all three together.
- Only elements with an `.id(...)` appear in the tree. In GPUI Kit 0.7.0 a Select's options are drawn but not published, so pick them with the keyboard.
